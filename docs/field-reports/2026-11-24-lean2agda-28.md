# 2026-11-24, lean2agda: four probes for the specialization of constants by universe level

+  **Date**: 2026-11-24.
+  **Harness**: Claude Code 2.1.331.
+  **Model**: Claude Fable 5.2 (Anthropic).
+  **Effort**: xhigh.
+  **Repository**: formalverification/lean2agda.
+  **Issue or pull request**: issue 28.
+  **Tools called**: check_file 5.

The session built a pass of the Lean to Agda translator that emits each
universe-polymorphic Lean constant as several Agda declarations, one per
pattern of its level parameters at zero, written in Lean.  The Agda it
wrote by hand was four small probe files, each asking one question about
Agda 2.8.0 that the design depended on: whether `#` can stand inside an
identifier, whether a file may declare more than one `BUILTIN REWRITE`
relation, whether such a relation may be `Prop`-valued, and what happens
to a rewrite rule whose left-hand side binds a variable only inside a
proof.  All four were settled through `check_file`, in five calls.  The
thousands of declarations the translator emitted were checked by the
project's own batch driver from the command line, not through the server.

+  **Tools used**.  `check_file` only, five calls of 50 to 170 ms each on
   files of 25 to 35 lines with no imports.  Three probes were accepted at
   the first call; one was rejected for my own scoping mistake and
   accepted at the second; the last was written to be rejected.
+  **What worked**.  The structured diagnostics did the work of reading
   the output for me.  The first probe's rejection came back as
   `NotInScope` with `candidates: ["Inner.Unit#z"]`, which was the fix:
   I had qualified a name with the file's own module.  The last probe's
   answer carried both the error and the warning that explained it, each
   with its code: `UnequalTerms` at the last definition, with `expected`
   and `actual` filled in, and before it
   `RewriteVariablesNotBoundByLHS` at the pragma, whose message names the
   variable.  The warning was the finding (Agda drops the rule, it does
   not refuse it), and a run that printed only the first error would have
   left me to guess why the equation failed.  `success` and
   `verdict.exitCode` made "accepted" a field to read, which is what a
   probe's first line records.
+  **What was awkward or missing**.  Nothing blocked.  Two small things:
   every answer names the project root as the probes' own directory
   (`rootSource: server-config`), which is right for files with no
   imports and would need a second look for one that imports the
   project's library; and for a probe that is meant to fail there is no
   way to say so, so the report of a successful experiment reads
   `success: false`.  A session keeps that straight itself; a field for
   the expected code would let the tool do it.
+  **Command line comparison**.  For these probes the server was the
   better loop: one call a file, no shell to enter, and the diagnostic's
   code and candidates in fields.  The command line would have cost a
   dev-shell entry per call and a read of prose.  For the bulk of the
   session's Agda, which was emitted text of one to two megabytes a tree
   run through a refusal loop that rewrites and rechecks each module many
   times under a heap bound, the command line driver was the only fit: it
   needs dozens of runs a module, per-module peak memory, and a detached
   process that outlives a call's time limit.

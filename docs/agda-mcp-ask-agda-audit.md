# Ask Agda rather than re-derive: the audit

File: `agda-native-air/docs/agda-mcp-ask-agda-audit.md`

Purpose: the audit record for issue #106 — every answer `agda-mcp` computes from source text, with a verdict on each, and the two measurements the issue asked for: what `--interaction-json` actually carries for the § 5 error corpus (Measurement 1), and what `--trace-imports=0` does to the `checkedFromSource` signal (Measurement 2).  Every probe below was run on 2026-08-20 against the pinned Agda 2.8.0 inside `nix develop .#backend`, and every quoted transcript was captured live from a real process; scratch directory prefixes are abbreviated to `…` in the quotes.  This is a standalone document rather than a section of `docs/agda-mcp-interaction-lane.md` because that file is #75's design record while this audit is a cross-tool inventory with its own acceptance list; the two cite each other.

## 1.  The rule

`answer = whatAgdaSaid <|> whatWeDerived`: when Agda can answer a question, ask Agda; a local derivation from source text is a pre-flight approximation and a fallback, never the authority, and a change in Agda's output degrades a field to the derived value and never to a wrong value.  That is issue #72's rule for Agda's prose ("the diagnostics text never gets a vote") applied to informational fields, with #100 as the worked example: `get_goal` scanned the file for its `module` field and reported a literate file under a name found in its prose, while Agda had already printed the true answer in output the same call had captured.  The normative, author-facing statement of the rule — the one a new tool's author is expected to read before writing a scanner — lives in `agda-mcp/README.md` under Architecture Notes ("Ask Agda rather than re-derive"); this document is the audit that applied it to the existing surface.

## 2.  The inventory

Every derived answer in the server, its verdict, and the issue that delegated it or would.  The issue predates #75 and #108 landing, so several rows are resolved by delivery; for those the audit's job is to record the resolution accurately, not to propose it.

| derived answer | where | verdict | issue |
| --- | --- | --- | --- |
| hole positions and spans | `AgdaMCP.Holes` | delegated | #75 (PR 107) |
| goal type and context | macro injection (`ensureDebugImport` + `reportGoalCtx`) | delegated | #108 (PR 110) |
| module name | `moduleNameOf` scan | delegated | #100 (PR 105), #108 (PR 110) |
| structured diagnostics | `AgdaMCP.Diagnostics` (#74) | stays, measured | Measurement 1 below; enrichment filed as #115 |
| project libraries and include paths | `AgdaMCP.Project` | stays, no interface exists | — |
| `checkedFromSource` | `AgdaMCP.Agda.checkedFromSourceOf` (#77) | derived-with-a-hole, detection filed | Measurement 2 below; #114 |
| the acceptance gate command | `AgdaMCP.Gate` | out of scope | #78 |

+  **The hole model — delegated, demotion recorded**.  `AgdaMCP.Holes` ports Agda 2.8.0's literate preprocessor and a model of its lexer to answer "where are the holes?".  Since #75 (PR 107) the interaction lane's `InteractionPoints` are the authority whenever Agda can load the file, and the design doc's § 1 states the demotion as policy: the lexical layer is "demoted, not deleted", remaining the splicing engine (a pre-Agda source edit structurally needs a source view: `fill_hole` and the injection path rewrite bytes), the code-only view, and the fallback for files Agda refuses to load.  The parity tests that were the old regime's only honesty check are now the demotion's enforcement: tier 2d pins the scan to batch Agda and the tier-3 lane tests pin it to the lane's `InteractionPoints` across the fixture matrix.
+  **The reporting-macro injection — delegated, fallback recorded**.  Since #108 (PR 110), `get_goal` asks the lane's `Cmd_goal_type_context` first: Agda's own goal display arrives as data, with no file mutation, and the response says `source: "interaction-lane"`.  The inject-patch-restore dance survives only as the stated fallback (`source: "injected-macro"`) for a lane that crashed, could not start, a file that does not load there, or a shutting-down registry — and as the one path that reports binder visibility, which Agda's goal display does not carry.
+  **The module name — delegated twice over**.  #100 (PR 105) re-sourced the batch path to `agdaModuleNameOf`, reading the name Agda resolved from its own `Checking M (path).` line; #108 (PR 110) strengthened the lane path with `liModule`, the name stored at load time so even a warm reuse knows it.  The code is literally the rule: `giModule = liModule li <|> moduleNameOf (flavourOf absPath) src`.  The scan persists in exactly two places, both correct: before the injection edit, where no Agda has spoken yet, and as the `<|>` fallback that keeps a successful answer complete when Agda named no module.
+  **Structured diagnostics — stays; the conjecture measured false in the strong form**.  Issue #106 conjectured that `--interaction-json` "emits structured information for the same errors" and asked how much of #74's parser it would retire.  Measurement 1 (§ 3) answers: the protocol's error payloads carry the same prose batch prints, wrapped in a JSON envelope; the envelope retires the parser's segmentation layer (block splitting, banner dedup, severity classification) and none of its content extraction (codes, line/col ranges, the `involved` payloads).  The one class where the protocol carries more than the prose — unsolved metas, whose names and types arrive as data — is filed as enrichment #115 rather than migration, because on that class the lane does not fail at all, and tolerance is exactly what the two-lane policy bars from verdict-adjacent surfaces.
+  **Project resolution — stays, and it is not an oversight**.  `AgdaMCP.Project` finds the nearest `*.agda-lib`, parses the libraries registry, and computes include paths.  No Agda query answers "what libraries and include paths apply to this file": `agda --help` offers none, and the interaction protocol is a consumer of the answer rather than a source — § 2.4 of the lane doc probed that `Cmd_load` with an empty argv does not even inherit a useful context, so the lane needs the resolved flags handed to it on every load.  Until Agda grows such a query, this derivation is the server's to own; it is kept honest by the response echo (#76), which shows the client the exact resolution every call used.
+  **`checkedFromSource` — derived honestly on three of four branches, and the fourth is now filed**.  The signal reads Agda's progress lines, which is asking Agda — but its warm branch is an inference from silence, and `--trace-imports=0` manufactures silence.  Measurement 2 (§ 4) reproduces the misreading end to end, closes every alternative arrival path for the flag, and records the decision: detectable wins over acceptable-and-documented, filed as #114.
+  **The project gate — out of scope**.  `AgdaMCP.Gate` decides which command is a project's acceptance gate by reading `Makefile`s and scripts.  That is not Agda's question; no delegation could exist.  Listed so the inventory is complete.

## 3.  Measurement 1: the error corpus over `--interaction-json`

Method: each fixture of the § 5 error corpus (`docs/feedback/flrp-agda-mcp-improvements.md`, fixtures under `agda-mcp/test/resources/diagnostics/`) was copied to a scratch directory and driven three ways: batch `agda` (prose + exit code), the real server's `get_diagnostics` over the MCP transport (what #74 extracts today), and a fresh `agda --interaction-json` child per fixture speaking the wire protocol of the lane doc's § 2 — flush the startup noise with a sentinel, `Cmd_load` with the resolved argv, sentinel again.  One fixture was added beyond § 5: `WarnOnly.agda` (an `EmptyPrivate` warning and nothing else), because warning-only runs are the case that motivated the parser's dedup heuristic.

The per-class result:

| error class | the protocol adds beyond batch prose | still prose-only in the protocol |
| --- | --- | --- |
| `UnequalTerms` | the message isolated in one JSON field; `JumpToError` start offset; an `atoms:["error"]` span with start and end character offsets | code, line/col range, expected/actual |
| `NotInScope` | same envelope | code, range, the did-you-mean candidates |
| `AmbiguousName` | same envelope | code, range, the qualified candidates and their provenance |
| `ClashingDefinition` | same envelope | code, range, the previous definition's origin |
| `ModuleDoesntExport` + `NotInScope` | the severity split is structural: the warning rides a `warnings` array beside the `error` object | each warning's code, range, and missing names, inside its `message` string |
| `UnsolvedConstraints` + `UnsolvedMetaVariables` | the load does not fail: metas arrive as structured `invisibleGoals` (name, type, line/col range each), the constraint error as prose in `AllGoalsWarnings.errors` | the constraint text; and the `[UnsolvedMetaVariables]` diagnostic is never emitted at all |
| `EmptyPrivate` (warning-only) | the warning appears once, structurally — no "All done" banner duplication — and `Status.checked` is `true` | the warning's content |

The representative transcripts, trimmed to the load-bearing lines.  A failed load (here `UnequalTerms.agda`) answers with the batch prose inside JSON, a start offset, and an error span whose `note` duplicates the same prose:

    {"info":{"error":{"message":"…/diag-corpus/UnequalTerms.agda:17.5-9: error: [UnequalTerms]\nBool !=< Nat\nwhen checking that the expression true has type Nat"},"kind":"Error","warnings":[]},"kind":"DisplayInfo"}
    {"filepath":"…/diag-corpus/UnequalTerms.agda","kind":"JumpToError","position":584}
    {"direct":true,"info":{"payload":[{"atoms":["error"],"definitionSite":null,"note":"…same message…","range":[584,588],"tokenBased":"NotOnlyTokenBased"}],"remove":false},"kind":"HighlightingInfo"}

The scope-warning pair separates severities structurally but each payload stays prose:

    {"info":{"error":{"message":"…/ModuleDoesntExport.agda:23.5-15: error: [NotInScope]\nNot in scope:\n  absentName\n  …"},"kind":"Error","warnings":[{"message":"…/ModuleDoesntExport.agda:20.24-50: warning: -W[no]ModuleDoesntExport\nThe module DiagBarrel doesn't export the following:\n  absentName\n…"}]},"kind":"DisplayInfo"}

The unsolved-meta fixture, which batch fails with two diagnostics (exit 42), does not fail on the lane at all — `Status.checked` stays `false`, but the load ends in `AllGoalsWarnings` plus `InteractionPoints`, and the § 5 ask ("each meta with its type") that the prose cannot carry arrives as data:

    {"info":{"errors":[{"message":"error: [UnsolvedConstraints]\nFailed to solve the following constraints:\n  _n_4 + _m_5 = 3 : Nat (blocked on _n_4)"}],"invisibleGoals":[{"constraintObj":{"name":"_n_4","range":[{"end":{"col":16,"line":28,"pos":1153},"start":{"col":9,"line":28,"pos":1146}}]},"kind":"OfType","type":"Nat"},{"constraintObj":{"name":"_m_5","range":[…]},"kind":"OfType","type":"Nat"}],"kind":"AllGoalsWarnings","visibleGoals":[],"warnings":[]},"kind":"DisplayInfo"}
    {"interactionPoints":[],"kind":"InteractionPoints"}

And the warning-only fixture, which batch prints twice (once raised, once under the "All done; warnings encountered" banner), arrives once, with `Status.checked: true`:

    {"info":{"errors":[],"invisibleGoals":[],"kind":"AllGoalsWarnings","visibleGoals":[],"warnings":[{"message":"…/WarnOnly.agda:2.1-8: warning: -W[no]EmptyPrivate\nEmpty private block."}]},"kind":"DisplayInfo"}

The verdict, per the issue's question "how much of #74's parser would the JSON protocol retire":

+  **Retired in principle**: the segmentation layer.  One message per JSON object retires block splitting; the absence of the banner duplication retires the dedup heuristic; the `error` / `warnings` / `AllGoalsWarnings.errors` envelope retires severity classification; `JumpToError` and the error atom add a character-offset position the prose states in line/col form.
+  **Not retired**: all four of the content defects the module header of `AgdaMCP.Diagnostics` records fixing.  The code (`[Code]` and `-W[no]Code`), the `LINE.COL-COL` ranges, the position-less headers (`error: [UnsolvedConstraints]` opens at column 0 on the wire too), and the `involved` payloads (expected/actual, candidates, origins, metas) are all inside `message` strings byte-identical to batch prose.  A lane-sourced diagnostics tool would run the same parser on the same prose, fished out of JSON fields; the parser is transport-independent content extraction, and nothing about the transport retires it.
+  **Changed semantics, which is the real boundary**: on the unsolved-meta class the lane does not fail, so lane-sourced "diagnostics" would disagree with the batch verdict on exactly the tolerance cases issue #69 was about — which is the two-lane policy's § 1 argument, met again from the other side.  `get_diagnostics` is a verdict-adjacent tool (it reports `success` from the batch exit code); it cannot re-source its evidence to a lane that refuses to fail.
+  **Exceeded, once**: the metas' names and types are data the prose never carries, one peek away in a warm lane's `AllGoalsWarnings` — filed as #115, mirroring #108's peek shape (enrichment, never a verdict input, cold lane changes nothing).
+  Two smaller observations, recorded but deliberately not filed: the character offsets (`position`, `range:[584,588]`) would need the file's text to become line/col, so "using the protocol's positions" would reintroduce a source-text derivation the prose already answers in line/col; and the lane's failed-load prose (`errorMessageOf`) could be fed through `parseDiagnostics` to give live-query failures structured payloads, a composition that works precisely because the parser is transport-independent — worth an issue the day a live-query client asks for it, not before.

So the conjecture's strong form is false for five of six classes, true in a useful sense for one, and the practical consequence is the opposite of a migration: #74's parser stays, unshared work stays zero (the parser already serves any prose, whichever pipe carried it), and the one structural surplus becomes #115.

## 4.  Measurement 2: `checkedFromSource` under `--trace-imports=0`

`checkedFromSourceOf` reads a completed run with no `Checking` line as interface reuse, because a warm `agda` exits 0 printing nothing.  The issue reported that `--trace-imports=0` silences the line outright, making a clean cold check read as warm.  Reproduced, extended to the lane, and every escape hatch probed:

+  **Level semantics, cold** (a two-module scratch project, caches scrubbed before each run): no flag and `--trace-imports=1` print the `Checking` lines (1 is the default level); `--trace-imports=0` prints nothing — the hole; `--trace-imports=2` and the bare `--trace-imports` add `Finished` lines; `--trace-imports=3` adds `Loading` for every interface read.  **Warm**: every level below 3 is silent; level 3 prints `Loading` lines, the only positive warm evidence the flag family offers.
+  **The misreading, through the real server**: a cold `check_file` on a clean module answers `checkedFromSource: true` with default flags and `checkedFromSource: false` with `--trace-imports=0` appended — the same source re-check, reported as warm.  The failing branch stays honest: a broken module under the flag answers `success: false` with the field absent (exit non-zero, no evidence either way), and the module name degrades to the declared-name fallback by the `<|>` rule.
+  **The lane has the same hole**: a cold `Cmd_load` whose per-load argv carries `--trace-imports=0` emits no `RunningInfo` at all — probed, the load went straight to `AllGoalsWarnings` — so `lrCheckedFromSource` (which feeds `get_goal`'s lane-path `checkedFromSource`) reads a genuine re-check as `false`, and the stored `liModule` stays empty (that one is covered by the fallback; the boolean is covered by nothing).
+  **Every other arrival path is closed**: `{-# OPTIONS --trace-imports=0 #-}` is rejected with `[OptionError] Unrecognized option`, and an `.agda-lib` `flags:` field carrying it is rejected identically — so the flag exists only on the command line the server itself assembles from its `--agda-flags`, `projectExtraFlags`, and `fileDirIncludeFlags`, in both lanes.  The grammar is closed too: `=N` is the only level-carrying spelling, bare `--trace-imports` means 2, a space-separated level does not parse (the `0` becomes a second input file, exit 71), and the last occurrence wins (`--trace-imports=0 --trace-imports=1` prints `Checking`; the reverse prints nothing).

**The recorded decision: detectable, filed as #114.**  The reasoning: the misreading sits on the field's most common branch (a clean check), and the field exists to explain latency, so a wrong "warm" defeats its purpose in a way an absent field does not — the #106 degradation ordering is absent over wrong.  Detection is complete because the arrival path is single and the grammar closed (both probed above), and it is cheap because the server already owns the argv it would scan.  The last-wins ordering even offers a repair — append `--trace-imports=1` when and only when the effective level is 0 — though that variant needs a version gate for foreign `--agda-bin` toolchains; both options and all the probe evidence are on #114, so nothing is re-derived there.  Until #114 lands, this section is the documentation of record for the behavior (the `agdaModuleNameOf` doc-comment already carries the flag's effect on the module name; the `checkedFromSourceOf` comment gains its caveat with #114's fix rather than as a drive-by edit here).

## 5.  The issue's third acceptance item, overtaken by events

The acceptance list asked for #75's description to be updated to say it retires the hole scanner and the macro injection, not just that it adds live queries.  That item is overtaken: #75 closed with PR 107, #108 (PR 110) subsequently moved `get_goal` itself onto the lane, and the design record both issues share already carries the claims in their accurate final form — § 1's lexical-layer bullet states the scanner is "demoted, not deleted … never again the authority for anything Agda can answer; the parity tests keep it honest against the lane's `InteractionPoints`", and § 4's `AgdaMCP.Tools.ProofState` entry states "the injection path remains as the fallback (`source: "injected-macro"`) … and it is the one path that reports binder visibility".  Both sections were re-read against merged main during this audit and carry the claims verbatim; "retire" would in fact overstate them, since the scanner splices and the injection reports visibility on purpose.  This resolution is recorded here and on issue #106 rather than by reopening a closed issue's text.
